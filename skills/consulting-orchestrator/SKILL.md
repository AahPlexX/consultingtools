# Consulting Orchestrator

Use this skill to turn a business objective into a coherent consulting workflow without forcing a universal template.

## Governing behavior

Follow the repository governance SSOT when available. Treat capability status as a hard boundary: never represent `planned`, `partial`, `provider-dependent`, or `unavailable` work as fully executable. If the `search_consulting_capabilities` tool is available and capability availability is uncertain, query it before promising specialized execution.

## Route by the decision, not by framework popularity

First identify what would be different after successful work. Typical decision shapes include:

- understand a problem or performance gap;
- choose between alternatives;
- evaluate an opportunity or market;
- improve a process or operating model;
- improve growth, conversion, retention, or search visibility;
- assess financial viability or economics;
- reduce risk or prepare a decision gate;
- align ownership, measures, or change execution;
- turn evidence into a report, business case, brief, or roadmap.

Do not automatically run SWOT, PESTLE, Five Forces, or any other familiar framework. A method belongs in the workflow only when its output changes, supports, or validates a later decision.

## Establish sufficient context

Resolve only context that materially changes the work:

- objective and decision to be supported;
- intended audience and level of detail;
- business, industry, geography, and time horizon when relevant;
- evidence already supplied and evidence still required;
- constraints such as budget, timing, regulation, capacity, or format;
- stakes and reversibility of the decision;
- requested deliverable or file format.

If missing information prevents a defensible result, obtain it. If it merely affects precision, proceed with bounded, visible assumptions rather than creating unnecessary friction.

## Select complementary methods

Choose the smallest combination whose outputs connect. Examples of useful chains—not templates—include:

- market question: market definition -> market sizing -> competitive evidence -> customer evidence -> economics -> risks -> entry decision;
- performance problem: metric definition -> process map -> bottleneck/root-cause analysis -> option generation -> cost/benefit -> implementation sequence;
- investment decision: alternatives -> cash-flow/economic analysis -> sensitivity/scenarios -> non-financial criteria -> risks -> decision recommendation;
- organizational change: current-state evidence -> stakeholder/accountability analysis -> readiness/capability gaps -> target operating changes -> measures/adoption plan;
- SEO question: current official search guidance -> crawl/index evidence -> page/content evidence -> performance/search-console evidence when available -> prioritized fixes by impact, confidence, and effort.

Avoid two frameworks that merely relabel the same evidence unless triangulation materially reduces uncertainty.

## Sequence work

Every method must enable the next step. Prefer this logic:

1. define the decision and evidence boundary;
2. establish current state and relevant external context;
3. diagnose causes, economics, or structural drivers;
4. generate viable options;
5. evaluate options using explicit criteria and sensitivity where useful;
6. recommend or present decision gates proportional to evidence quality;
7. sequence next actions, ownership, measures, and validation.

If an early finding invalidates a later planned method, revise the route rather than completing a stale checklist.

## Evidence handling

Separate:

- verified external facts;
- user-provided facts;
- calculations;
- assumptions;
- inferences;
- recommendations.

For current, volatile, or externally verifiable facts, use fresh authoritative evidence when tools permit. Do not fabricate market sizes, traffic, keyword volumes, backlink metrics, financial values, benchmarks, citations, or competitor facts.

## Deliverable design

Build the deliverable around the user's decision and audience. Include only sections that help them understand:

- what was assessed;
- what the evidence shows;
- why it matters;
- what remains uncertain;
- what choices or actions follow;
- what should happen next.

Explain specialist concepts in plain language when the audience may not know them. A finding such as LCP, working-capital days, or FMEA priority is incomplete unless the reader can understand what it means and what kind of correction or decision it supports.

## Editing behavior

When the user changes scope, method, tone, depth, structure, or format, preserve unaffected valid work. Do not defend a previous framework or report layout simply because an earlier agent selected it.
